# Client internationalization (i18n)

How the Tauri client's language layer works, and the rules you need to follow when adding or
changing user-facing text.

This document describes how the client's language layer works. It is contributor documentation
for the client workspace, not a release note.

## Background: what was already there

The core editor package (`packages/cherry-markdown`) has shipped a complete locale bundle for a
long time. `src/locales/en_US.js` holds 208 keys, exactly matching `zh_CN.js`, and `ru_RU.js`
exists alongside them. The core also ships a `ChangeLocale` toolbar hook
(`src/toolbars/hooks/ChangeLocale.js`) that offers Chinese, English, and Russian.

Two things kept that from being usable:

1. `ChangeLocale` is not in the core's default toolbar array (`Cherry.config.js`), so a consumer
   has to opt in.
2. The client hardcoded `locale: 'zh_CN'` and had no locale plumbing of its own. Every
   user-visible string in the client shell was a hardcoded Chinese literal.

So the fix was never "restore English to the core". The core was fine. The client was the only
Chinese-only surface, and that is what this change addresses.

The core library, the VS Code plugin, the mini-program package, and the `examples/` demo site are
all deliberately out of scope here. See "Known gaps" at the bottom.

## Architecture

Three files under `packages/client/src/i18n/`:

| File | Role |
| --- | --- |
| `zh_CN.ts` | Simplified Chinese copy. Exports `TranslationTree`. |
| `en_US.ts` | English copy. Structurally identical to `zh_CN.ts`. |
| `index.ts` | The runtime: `t()`, `resolveInitialLocale()`, `toBcp47()`, `useI18n()`. |

18 top-level sections, 214 leaf entries. Sections are grouped by surface: `common`, `file`,
`directory`, `shortcut`, `storage`, `unsavedDialog`, `statusBar`, `settings`, `versionHistory`,
`exportAction`, `imageBed`, `recent`, `explorer`, `sidePanel`, `contextMenu`, `editor`,
`milkdown`, `app`.

### The `t()` API

```ts
t('settings.title');                                  // 'Settings'
t('statusBar.charCount', { count: 12 });              // '12 chars'
t('exportAction.exportedMarkdown', { path });        // 'Exported Markdown: /tmp/a.md'
```

`translate()` resolves a dotted key against the active bundle, then falls back to `zh_CN`, then
falls back to returning the key string itself. That last fallback is deliberate: a missing key
renders as a visible key name, which is an obvious bug signal rather than a blank element. In dev
builds a `console.warn` names the offending key.

### How reactivity works

`index.ts` owns a module-level `ref` holding the active locale. `t()` reads that ref on every
call, which gives two behaviours for free:

- Called inside a `h()` render function, the read is tracked, so Vue re-renders the component
  when the locale changes. No event bus, no manual trigger, no `key` bump.
- Called from a plain function (a toast, an error path, imperative DOM), it is a snapshot of the
  current value. That is the correct behaviour for those call sites.

The i18n module deliberately does **not** import Pinia. That would create a cycle, because
`store/modal/preferences.ts` imports `resolveInitialLocale()` to seed the default. The store is
the single source of truth and writes into the i18n runtime through `setActiveLocale()`; the
runtime never writes back.

## The rule that will bite you

**`t()` must be called during render. Never hoist it into a module-level constant.**

This compiles without error and silently does not update:

```ts
// WRONG: evaluated once at import, before the locale is ever hydrated
const TITLE = t('settings.title');
```

Module-level `t()` runs at import time. `setActiveLocale()` runs later, in `main.ts`. The
constant is frozen at the default locale forever, and nothing warns you.

Store the key and translate at use time:

```ts
// RIGHT
const TITLE_KEY = 'settings.title';
// ... inside the render function:
h('h3', { class: 'dialog-title' }, t(TITLE_KEY))
```

The same rule applies to every constant that holds user-facing text, including the view-mode
options in `StatusBar.tsx` (which store `labelKey` / `titleKey`) and the panel definitions in
`side-panel/types.ts` (which store `labelKey`). Those types were deliberately renamed to make the
key, not the text, the thing you pass around.

## How language switching works

One control drives everything: the core's own `ChangeLocale` toolbar button, registered by adding
`CHANGE_LOCALE_HOOK` to the `toolbar` array in `CherryMarkdown.ts`.

```
core ChangeLocale button
        |
        v
  afterChangeLocale event  --->  preferences.setLocale()  --->  setActiveLocale()
                                      |                              |
                                      |                              v
                                      |                    every t() re-renders
                                      |
                                      +<--- watch(preferences.locale) ---+
                                              setLocale() + resetToolbar()
```

Two directions, each guarded by an equality check so neither can retrigger the other.

**Editor to store.** The core button updates its own locale and calls `resetToolbar` itself, then
emits `afterChangeLocale`. The client writes that into the preferences store.

**Store to editor.** Changing the language in Settings writes to the store. A `watch` in
`useCherryEditor.ts` pushes it back into the core and calls `resetToolbar` explicitly.

That explicit `resetToolbar` is not optional. `Cherry.setLocale()` (`Cherry.js:1262`) sets
`options.locale` and `this.locale` and emits, but unlike the built-in `ChangeLocale.onClick` it
does **not** re-render the toolbar. Without the extra call, the toolbar labels would sit at the
old language while the rest of the UI switched. This is the single easiest way to reintroduce a
mixed-language window, so do not remove it.

### Custom menu hooks

The three client menu hooks (Edit, Save, Export) pass neutral keys (`clientEdit`, `clientSave`,
`clientExport`) to `Cherry.createMenuHook`, and the actual labels come from the `locales` object on
the Cherry config. `MenuBase.createBtn` resolves button titles via `this.locale[this.name]`, so
the core translates them in the active language automatically. The keys in `cherryConfig.locales`
must stay in sync with the first argument to `createMenuHook`.

## Other surfaces

**Imperative DOM.** The Milkdown plugins (`slashMenu.ts`, `selectionTooltip.ts`,
`blockHandle.ts`) build DOM with `document.createElement`, so they cannot re-render reactively.
They call `t()` at build time. `window.prompt` in `selectionTooltip.ts` is called at interaction
time and picks up the new language naturally.

**Dates.** `RecentPanel.tsx` and `fileUtils.ts` use `Intl.DateTimeFormat` and
`Intl.RelativeTimeFormat` with `toBcp47(locale)`, which removes the hand-written weekday array
and the manual "N minutes ago" strings. `AppLocale` is underscore-joined (`en_US`) but `Intl` needs
BCP 47 (`en-US`), hence the `toBcp47()` helper.

**`document.documentElement.lang`** is set once in `main.ts` at startup and kept in sync by a
`watch` in `App.tsx`.

**Exported documents.** `useCherryExport.ts` sets `<html lang>` on exported HTML from the app's
selected locale rather than from `navigator.language`, so an export always matches what the user
is looking at.

## Adding a string

1. Add the key to **both** `zh_CN.ts` and `en_US.ts`. The parity test will fail if you forget.
2. Use `{name}` placeholders for anything dynamic. Unknown placeholders are left intact rather
   than rendering `undefined`.
3. Call `t()` at the use site, in the render function. See the rule above.
4. If the string is shown by a constant or type that holds labels, add a `*Key` field to the type
   rather than a string field.
5. Run the tests: `yarn workspace @cherry-markdown/client test` or `vp run -F
   @cherry-markdown/client test`.

## Tests

`packages/client/test/i18n.spec.ts`, 17 tests. The client had no test runner before this change;
`vitest.config.ts` and a `test` script were added for it. The suite covers:

- **Key parity.** `zh_CN` and `en_US` must expose identical key sets, and identical nesting
  shape. This is the highest-value test in the suite, because silent key drift is the main way
  this system degrades.
- **No blank values** in either bundle.
- **Fallback chain**: active locale, then `zh_CN`, then the key itself.
- **Interpolation**, including that an unknown placeholder stays literal.
- **Locale resolution**: `en-US`, `en-GB`, `zh-CN`, `zh-TW` map correctly; `fr-FR`, an empty tag,
  and a missing `navigator` all fall back to `zh_CN`.
- **`toBcp47()`** output is accepted by `Intl`.

## First-launch behaviour

With no stored preference, the client reads `navigator.language`:

- starts with `zh` or `en`, case-insensitive, mapped directly
- anything else falls back to `zh_CN`

A stored preference always wins over detection. Existing installations that already have a
`cherry_markdown_ui_preferences` blob but no `locale` key get one detection pass on upgrade, then
their choice is persisted from that point on.

Note that WebView2 reports the user culture rather than the Windows system locale in most setups.
A machine with an `es-MX` system locale and an `en-US` user culture resolves to English. If the
system display language is ever changed to something outside `zh` and `en`, first launch will fall
back to Chinese until the user picks a language in Settings.

## Known gaps

**The CodeMirror placeholder and the theme dropdown labels** are set when the Cherry editor is
constructed, in `cherryInstance()`. A language switch does not update them live; they take effect
when the editor is next created, for example after an engine switch. Every other surface updates
immediately.

**`setLocale` does not persist when the value is unchanged.** If you open Settings and select the
language that is already active, the action short-circuits before `saveToStorage`, so nothing is
written and the app re-detects from the OS on the next launch. It only becomes visible if the OS
language changes afterwards. Making `setLocale` always persist would close this.

**First launch does not persist the detected locale at all.** Detection seeds the default, but
only the `set*` actions write to `localStorage`.

**`changeLocale` is missing from the core's `CherryDefaultToolbar` type union**, even though
`HookCenter.js` registers the hook. Since the core is out of scope here, `CherryMarkdown.ts`
carries one documented local cast, `CHANGE_LOCALE_HOOK`. Delete it once upstream fixes the type.

**Console diagnostics were deliberately left in Chinese.** Around 40 `console.warn` and
`console.error` calls across the client are developer-facing and never shown to users, so they
were left untouched. Code comments are Chinese for the same reason: the entire codebase is
commented in Chinese, and translating them would produce an enormous diff with no user benefit.

**Out of scope, still Chinese:** the formula bubble category titles in
`packages/cherry-markdown/src/toolbars/BubbleFormula.js` (hardcoded, bypass the core locale
system), the graph and echarts insert-menu example content, and the `examples/` demo pages. These
are recorded here so a follow-up effort can pick them up.

## Commands

```shell
# client tests
vp run -F @cherry-markdown/client test

# typecheck and build
vp run -F @cherry-markdown/client build

# run the desktop client
yarn dev:client
```

A quick manual check after changing any language code: switch languages from the editor toolbar and
from Settings, in both directions, and confirm the toolbar and the app shell change together.
That mixed-language regression is the one the automated tests cannot catch.
